# 职路启航项目验收通过规划

本文档根据《软件工程课程实践项目验收要求（2024级雷军班）》整理，用于指导“职路启航 · 应届生求职赋能平台”完成现场验收和最终文档提交。

## 一、验收结论判断

当前项目已经具备通过课程验收的基础。

优势：

- 已形成可演示业务闭环：学生简历制作、AI 润色、教师审核、批注评分、岗位投递、求职进度、提醒、管理员监管、站内通知。
- 技术栈完整：Spring Boot + MyBatis + MySQL + JWT + Vue 3 + Element Plus。
- 已有较多开发文档：需求规格说明、当前状态、下一阶段计划、教师审核体系计划、管理员后台计划、企业端计划、README。
- 后端测试和前端构建已验证通过。

主要风险：

- 项目功能多，15 分钟现场报告容易超时。
- 文档需要按验收要求重新整理归档，而不是只提交散落的开发过程文件。
- 生产系统成熟度仍有限，答辩时应主动说明：密码明文、企业端未实现、真实 PDF/真实推送/生产部署未完成。
- 需要准备演示视频，避免现场环境或网络导致演示失败。

总体策略：

```text
现场验收突出“完整闭环 + 软件工程过程 + AI 协作 + 业务价值”。
最终提交突出“文档齐全 + 结构清晰 + 命名规范 + 可复现部署”。
```

## 二、现场验收评分点与应对策略

### 1. 验收准备，5 分

要求：

```text
提前完成验收准备
PPT、开发文档提前拷贝到教室机器
或提前调试好自带机器环境和投影连接
```

应对：

- 提前准备一个 `验收现场材料/` 文件夹。
- 文件夹中包含：
  - 验收汇报 PPT
  - 演示视频 MP4
  - 项目运行截图
  - README
  - 课程实践报告 PDF
  - 核心开发文档 PDF 或 Word
- 至少提前一天在本机完整跑通：
  - 后端 `.\mvnw.cmd clean test`
  - 前端 `npm run build`
  - 本地 MySQL 数据库
  - 登录四类示例账号
- 验收当天优先使用演示视频，现场系统作为备选补充。

### 2. 时间控制，5 分

要求：

```text
生产小组 PPT 报告 + 系统演示总计不超过 15 分钟
现场安装软件、切换演示、报告人更换都计入时间
不接受现场调换报告顺序
```

建议时间分配：

```text
0:00 - 1:00   项目背景与问题
1:00 - 2:00   用户需求与系统目标
2:00 - 4:00   软件工程过程：需求、设计、实现、测试
4:00 - 6:00   系统架构与核心模块
6:00 - 8:00   系统特色、AI 协作、业务价值
8:00 - 12:00  演示视频或现场演示
12:00 - 14:00 挑战、问题与解决方案
14:00 - 15:00 总结与后续改进
```

演示视频建议控制在 4 分钟左右，最多 5 分钟。

### 3. PPT，5 分

要求：

```text
要素齐全
文字通顺，无错别字
图表规范，比例适当
最后一排能看清
```

PPT 建议结构：

```text
1. 封面：项目名、团队、成员、课程信息
2. 领域背景：应届生求职痛点
3. 用户需求与系统目标
4. 用例与角色：学生、教师、管理员，企业端规划
5. 系统架构：前端、后端、数据库、AI 服务
6. 数据库设计：核心 ER 图或表关系
7. 核心流程一：简历制作与 AI 润色
8. 核心流程二：教师审核、批注评分、返回版本
9. 核心流程三：岗位投递、进度、提醒、经验记录
10. 管理员监管与站内通知
11. 软件工程方法：需求、设计、实现、测试、迭代
12. AI 协作内容
13. 系统特色与业务价值
14. 挑战与解决方案
15. 总结与后续计划
```

控制建议：

- 每页少字，多图。
- 字号不低于 24。
- 架构图、流程图、ER 图优先用图展示。
- 不展示长代码，只展示关键接口或模块结构。

### 4. 表达，5 分

要求：

```text
声音洪亮
不是全程念 PPT
口头内容与 PPT 同步
可以多人报告
```

建议：

- 2 到 3 人分工讲解。
- 每人负责固定部分，避免现场频繁切换。
- 每页准备 2 到 4 句讲稿，不逐字念。
- 演示视频播放前先说明“接下来展示学生、教师、管理员三端闭环”。

### 5. 生产小组报告与演示，40 分

要求覆盖：

```text
领域背景和存在的问题
用户需求和系统目标
软件工程方法在开发过程中的运用：分析、设计、实现

与 AI 合作完成的内容
实践中面临的挑战和解决方案
系统演示：3 到 5 分钟视频，展示产品特色、核心功能、典型场景和业务价值
```

本项目建议重点讲：

#### 背景与问题

```text
应届生简历表达弱
求职过程分散，投递进度难管理
学生缺少教师针对性反馈
教师审核过程缺少结构化记录
管理员缺少平台监管视图
```

#### 用户需求

```text
学生：制作简历、AI 润色、投递岗位、追踪进度、查看教师反馈
教师：接收审核请求、批注评分、返回修改版
管理员：审核教师、监管用户、查看审核记录、处理撤回、维护平台设置
```

#### 系统目标

```text
构建一个覆盖“简历准备 - 教师指导 - 岗位投递 - 求职进度 - 平台监管”的求职赋能平台。
```

#### 软件工程方法

可以按下列内容讲：

```text
需求分析：角色识别、用例拆分、功能优先级排序
系统设计：三端角色架构、REST API、数据库表设计
迭代实现：先完成 MVP，再逐步扩展教师审核、岗位投递、通知等模块
测试验证：后端 Maven 测试、前端 Vite 构建、核心流程手工验收
文档管理：需求规格、计划文档、当前状态文档、README
```

#### 系统特色

建议突出：

```text
多简历管理，每份简历是独立实体
AI 润色结果不自动覆盖，需学生主动采纳
教师返回新简历不覆盖原简历，而是创建新版本
教师可字段级批注和评分
学生可撤回已接受审核请求，管理员介入处理
岗位投递与求职进度、经验记录、提醒联动
管理员后台可监管教师、用户、简历、审核、日志、设置
站内通知连接关键业务动作
```

#### AI 合作内容

可以分两类讲：

```text
系统功能中的 AI：
DeepSeek 简历润色，结构化返回 title/name/education/experience/skills 等字段。
后端增强 JSON 解析，避免 AI 返回格式波动导致功能失败。

开发过程中的 AI：
辅助需求梳理、模块计划、代码实现、测试排查、README 和验收规划整理。
```

#### 挑战与解决方案

建议准备 4 个：

```text
挑战 1：教师返回简历不能覆盖学生原始简历
解决：使用 source_resume_id、generated_by_teacher_id、version_type 建立版本链。

挑战 2：审核请求涉及多角色权限
解决：在 Controller 中按 STUDENT/TEACHER/ADMIN 严格校验资源归属。

挑战 3：AI 返回 JSON 不稳定
解决：使用 response_format、低 temperature、严格 prompt，并增强后端 JSON 提取和字段兼容。

挑战 4：求职流程跨度长，数据分散
解决：用 job_application 串联岗位、简历、状态、经验记录和提醒。
```

### 8. 回答问题，20 分

现场可能提问与建议回答：

#### 问：项目最核心的业务闭环是什么？

答：

```text
学生创建简历并使用 AI 润色，提交给教师审核；教师接受后进行字段级批注、评分并可返回新版本；学生再用简历投递岗位，维护投递进度、经验记录和提醒；管理员负责监管用户、教师、审核和通知。
```

#### 问：为什么教师返回简历不覆盖原简历？

答：

```text
为了保留学生原始版本和教师修改版本的可追溯性。系统使用 source_resume_id 和 version_type 建立版本链，教师返回时创建新的 resume 实体。
```

#### 问：AI 润色如何避免编造？

答：

```text
后端 prompt 明确禁止编造学校、项目、奖项、公司、技术栈和成果数字；AI 只允许改写已有信息。返回结果不会自动保存，必须由学生确认采纳。
```

#### 问：当前项目为什么还不能生产上线？

答：

```text
当前定位是课程实践原型，业务闭环已经完整，但生产化还需要密码加密、隐私字段保护、HTTPS、日志脱敏、更多自动化测试和运维部署配置。
```

#### 问：管理员后台的定位是什么？

答：

```text
管理员不是深度业务运营者，而是平台监管者，主要负责教师审核、用户管理、审核请求监管、撤回处理、操作日志和平台设置。
```

#### 问：企业端为什么没有实现？

答：

```text
当前已完成企业端前置能力：岗位库和投递记录。企业账号、企业资料审核、企业发布岗位和处理申请已经单独规划在 docs/company_service_plan.md 中，作为后续独立阶段，避免影响当前学生-教师-管理员核心闭环。
```

## 六、15 分钟现场汇报推荐讲稿骨架

```text
大家好，我们小组的项目是“职路启航：应届生求职赋能平台”。

这个项目面向应届毕业生求职过程中的三个核心问题：
第一，简历表达不专业；
第二，投递和求职进度分散；
第三，学生很难获得结构化、可追踪的教师反馈。

围绕这些问题，我们设计了学生、教师、管理员三类角色。
学生可以制作多份简历、使用 AI 润色、投递岗位、追踪进度；
教师可以接收审核请求、进行字段级批注和评分、返回修改版本；
管理员负责教师审核、用户管理、审核监管、撤回处理和平台设置。

在软件工程方法上，我们先进行需求分析和角色用例拆分，
再设计数据库和系统架构，然后按迭代方式逐步实现 MVP、教师审核、岗位投递、通知等模块。

系统的核心亮点有三个：
第一，AI 润色不直接覆盖简历，学生确认后才采纳；
第二，教师返回版本不会覆盖原简历，而是形成版本链；
第三，审核、投递、提醒、通知和管理员监管形成完整闭环。

接下来通过 4 分钟演示视频展示核心流程。
```

## 七、最终建议
