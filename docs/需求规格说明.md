# 《职路启航·应届生求职赋能平台》需求规格说明书

[toc]



## 1. 引言

### 1.1 编写目的

本需求规格说明书用于全面描述“职路启航·应届生求职赋能平台”的功能需求、数据需求及系统建模结果，为系统设计、开发与测试提供依据，同时作为项目验收标准。

### 1.2 项目背景

随着就业竞争加剧，应届生在求职过程中面临如下问题：

- 简历制作不规范、缺乏针对性
- 岗位匹配效率低
- 求职流程缺乏统一管理
- 招聘信息分散且滞后
- 缺乏个性化求职指导 

本系统旨在提供一体化解决方案。

### 1.3 项目范围 (Scope) 

本系统旨在为应届毕业生提供一个集简历智能化制作、精准岗位匹配、求职全流程管理于一体的赋能平台。

- **包含的功能：** 用户身份认证、基于行业模板的简历编辑器、AI 简历优化建议算法、岗位检索与相似度推荐、投递状态实时追踪、导师在线评阅系统。
- **不包含范围：** 本系统不涉及企业方的面试预约排期管理（仅记录状态）、不提供真实的在线交易或支付功能、不承担外部招聘平台数据的真实性审核。

## 2. 总体描述

### 2.1 产品视角 

“职路启航”平台是一个独立的 Web 应用程序。它作为学校就业指导中心信息化生态系统的重要补充，向上通过 API 接入学校统一身份认证系统获取学生基础学籍数据，向下对接主流招聘平台（如 Boss 直聘、拉勾网）的公开接口获取实时岗位信息。

### 2.2 用户角色

#### 2.2.1 核心用户：应届生

- 使用简历制作、岗位匹配、求职管理功能

#### 2.2.2 次要用户：求职指导老师

- 审核简历、提供建议

#### 2.2.3 通用用户

- 注册、登录、管理个人信息

### 2.3 系统目标

1. 提供行业化简历模板与优化建议
2. 实现岗位精准匹配
3. 支持求职全流程管理
4. 聚合招聘信息
5. 提供个性化指导 

### 2.4 运行环境（待定）

- **服务器端：** 运行于 Linux (Ubuntu 20.04+) 操作系统，支持 Docker 容器化部署。
- **数据库：** MySQL 8.0 关系型数据库，Redis 6.0 缓存服务。
- **客户端：** 兼容主流浏览器，包括但不限于 Chrome (80+), Microsoft Edge, Safari (12+)。
- **网络环境：** 支持 HTTPS 协议，建议带宽不低于 5Mbps。

### 2.5 假设与依赖

1. **外部 API 稳定性：** 假设第三方 AI 大模型接口及招聘平台 API 的可用性不低于 99%。
2. **数据格式假设：** 假设用户上传的附件简历均为 PDF 或标准 Word 格式。
3. **身份依赖：** 系统运行依赖于学校身份认证服务器提供的实时鉴权响应。

##### 3.1.1.2 用例场景描述

该用例描述应届生使用系统进行智能简历制作的全过程。

用户首先进入“简历制作”模块，并选择目标行业与岗位（如互联网-产品经理）。系统根据岗位信息，从模板库中推荐匹配的简历模板。用户在模板基础上填写个人信息，包括基本信息、教育经历以及项目或实习经历。

完成信息录入后，系统调用岗位匹配分析模块，对简历内容进行智能分析，主要包括关键词匹配、内容完整性检查以及表达优化建议（如内容精简、结构优化、关键词补充等）。

用户可实时预览简历效果，并根据建议进行修改。最终用户可以选择导出PDF或保存简历，进入后续版本管理流程。

异常情况下：

- 若信息缺失，系统提示用户补充必要字段
- 若模板加载失败，则自动切换为默认模板继续流程

#### 3.1.2 精准岗位匹配与投递 (prod. by 覃子倍)

3.1.2.1 用例信息

**用例名称**：精准岗位匹配与投递

**用例编号**：UC-3.2

**参与者**：应届生（用户）

**系统参与者**：岗位匹配系统、简历服务模块、岗位数据库、投递服务模块、投递记录库

**前置条件**：

- 用户已完成简历制作
- 用户已设置求职意向（行业/城市/薪资等）

**后置条件**：

- 简历成功投递至目标岗位
- 投递记录已保存
- 求职进度更新为“已投递”

**核心目标**：

基于用户简历与求职意向，实现岗位智能匹配并支持一键投递与记录管理

##### 3.1.2.2 用例场景描述

用户首先在系统中输入或更新求职筛选条件，包括目标行业、工作城市以及薪资范围。系统根据用户的简历内容与求职偏好，在岗位数据库中进行匹配计算，筛选出符合条件的岗位列表。

用户可以浏览岗位详情，包括岗位职责、要求及公司信息。当用户决定申请某个岗位时，点击“一键投递”按钮，系统自动调用用户已完成的简历，并通过投递服务模块将简历发送至目标企业或岗位系统。

投递完成后，系统会记录本次投递信息，包括岗位ID、投递时间与投递状态，并更新用户求职进度为“已投递”。

异常情况下：

- 若网络异常或接口失败，则提示投递失败并允许重试
- 若岗位已失效或被下架，则提示用户更新岗位信息

#### 3.1.3 求职进度管理 (prod. by 史宇硕)

##### 3.1.3.1 用例信息

**用例名称**：求职进度管理

**用例编号**：UC-3.3

**参与者**：应届生（用户）

**系统参与者**：求职进度管理模块、投递记录库、企业反馈接口、提醒服务模块、用户经验记录库

**前置条件**：

- 用户至少存在一条投递记录

**后置条件**：

- 求职进度状态更新完成
- 提醒任务成功创建并生效
- 用户经验记录已保存
- 企业反馈数据已同步

**核心目标**：
对用户的求职全过程进行状态追踪、提醒管理与经验沉淀，实现投递后的闭环管理

------

##### 3.1.3.2 用例场景描述

用户进入“求职进度管理”模块后，系统首先从投递记录库中读取该用户的所有投递信息，并根据企业反馈数据更新当前求职状态，包括“已投递、筛选中、笔试、面试、Offer”等阶段。

用户可以查看每一条岗位申请的最新进展，并针对关键节点（如笔试、面试）设置提醒。系统调用提醒服务模块生成定时提醒任务，在指定时间通过系统通知或消息推送提醒用户。

同时，用户可以对每一次求职过程进行经验记录，例如面试问题、公司反馈、准备心得等，这些内容将存储在用户经验记录库中，用于后续复盘。

系统还会定期或实时同步企业反馈接口的数据，例如面试结果或状态更新，并自动更新用户求职进度。

异常情况下：

- 若企业反馈数据未能及时同步，系统允许用户手动更新状态
- 若提醒服务失败，系统会记录失败日志并尝试重新调度

#### 3.1.4 简历审核与批注 (prod. by 邓佳杰)

##### 3.1.4.1 用例信息

**用例名称**：简历审核与批注

**用例编号**：UC-3.4

**参与者**：求职指导老师

**系统参与者**：简历管理模块、简历数据库、批注服务模块、评分管理模块、反馈通知模块、学生用户

**前置条件**：

- 学生已提交简历审核申请
- 系统中存在待审核简历

**后置条件**：

- 简历批注与评分已保存
- 学生已收到审核反馈
- 简历状态更新为“已审核”

**核心目标**：
实现教师对学生简历的在线审核、批注与评分，并将反馈高效传递给学生

##### 3.1.4.2 用例场景描述

求职指导老师登录系统后，进入“简历审核”模块，系统首先从简历数据库中加载所有待审核简历列表。老师可以选择任意一份简历进行查看，系统展示完整简历内容，包括个人信息、教育背景、项目经历等。

在查看过程中，老师可以对简历进行批注操作，包括添加文本说明（如修改建议、表达优化建议）以及结构性标记（如高亮问题段落、标记需修改区域）。

完成批注后，老师对该简历进行综合评分，用于反映简历质量水平。评分与批注信息一并提交至系统。

系统将审核结果写入数据库，并通过反馈通知模块将结果推送给学生用户，学生可以在个人端查看具体修改建议与评分结果。

异常情况下：

- 若简历加载失败或网络异常，系统提示错误并允许重新加载
- 若提交失败，系统会暂存批注内容并支持重新提交

### 3.4. 状态转换图

#### 3.4.1 状态图与总体说明

![StateAll](D:\files\study\SE\Code\out\pic\StateAll\StateAll.png)

该状态图用于描述求职管理系统在用户使用过程中的整体状态变化逻辑。系统围绕“简历生成—岗位投递—求职进度管理”三条主线展开，并引入简历审核反馈机制，形成闭环优化流程。

整体状态机采用自顶向下结构设计，包含三个核心子状态模块：

- 简历状态
- 投递状态
- 求职进度状态

系统通过关键事件驱动不同模块之间的状态迁移。

#### 3.4.2 简历状态模块说明

简历状态模块用于描述用户从初始创建简历到最终优化完成的全过程，其主要状态包括：

- 草稿：用户初始创建简历
- 基本信息已填：完成基础信息录入
- 模板生成：系统根据岗位方向生成推荐模板
- 简历优化：系统或用户对内容进行优化调整
- 简历完成：简历已基本定稿
- 审核中：提交给指导老师进行审核
- 已反馈：收到审核意见

状态之间的核心特点为“迭代优化机制”，其中“已反馈 → 简历优化”构成闭环，使简历能够持续改进。

#### 3.4.3 投递状态模块说明

投递状态模块用于描述用户将简历应用于岗位投递的过程，其状态包括：

- 未投递：尚未进行岗位申请
- 岗位匹配：系统根据简历进行岗位推荐
- 已投递：完成投递动作
- 投递成功：企业接收简历
- 投递失败：投递异常或岗位失效

其中，“投递失败 → 岗位匹配”表示系统支持重新匹配与再次尝试投递，保证投递流程的可恢复性。

#### 3.4.4 求职进度状态模块说明

求职进度模块是系统的核心业务状态机，用于描述用户投递后的招聘流程演化过程，包括：

- 已投递：投递完成后的初始状态
- 筛选中：企业进行简历筛选
- 笔试：进入笔试环节
- 面试：进入面试环节
- Offer：获得录用结果
- 拒绝：未通过招聘流程

该模块体现典型招聘生命周期，状态单向递进，最终收敛至“Offer”或“拒绝”终止状态。

#### 3.4.5 模块间状态关联说明

三个子状态模块之间通过关键事件进行连接，形成完整求职流程：

- “简历完成 → 未投递”：表示简历可用于投递
- “已投递 → 求职进度”：表示进入招聘流程管理阶段
- “已反馈 → 草稿”：表示简历优化闭环
- “Offer → 系统结束”：表示求职流程完成

该设计实现了从“简历生成”到“求职结果”的完整生命周期闭环。

#### 3.4.6 设计总结

该状态图采用分模块分层设计思想，将复杂求职流程拆解为三个相对独立但逻辑关联的状态子系统，实现以下目标：

- 清晰表达用户求职全生命周期
- 支持简历优化的迭代机制
- 覆盖投递与招聘流程状态演化
- 构建反馈驱动的闭环系统

整体设计符合软件工程中“高内聚、低耦合”的建模原则，适用于需求分析与系统设计阶段的建模表达。

## 4. 外部接口需求

### 4.1 用户接口

- 采用响应式 Web 设计，自动适配 PC 端与移动端浏览器。
- 界面遵循“极简逻辑”原则，核心功能（如简历编辑）的层级深度不超过 3 层。
- 提供标准的提示信息反馈机制，所有异步操作（如保存、AI 分析）需有明确的状态加载指示。

### 4.2 软件接口

- **认证接口：** 采用 OAuth 2.0 协议连接学校统一身份认证系统。
- **AI 引擎接口：** 通过 RESTful API 发送 JSON 格式数据至后端大模型分析服务。
- **通知接口：** 调用 SMTP 协议邮件网关发送求职状态更新提醒。

### 4.3 通信接口

- 全站采用 TLS 1.2/1.3 加密传输。
- API 调用遵循标准的 REST 架构风格，使用 HTTP 动词（GET, POST, PUT, DELETE）定义操作。

## 5. 系统属性/非功能需求

### 5.1 可靠性 (Reliability)

- **可用性：** 系统全年可用率应达到 99.5% 以上。
- **故障恢复：** 若系统发生崩溃，数据丢失量（RPO）应小于 5 分钟，系统恢复时间（RTO）应小于 30 分钟。

### 5.2 安全性 (Security)

- **数据加密：** 学生的手机号、邮箱等隐私字段在数据库中需进行 AES-256 对称加密。
- **权限控制：** 采用基于角色的访问控制（RBAC），严格限制指导老师只能访问其对应院系/班级的学生数据。
- **审计日志：** 系统需记录所有关键操作（如修改简历、删除记录）的操作人 IP 及时间戳。

### 5.3 可维护性 (Maintainability)

- 代码应遵循模块化设计，业务逻辑层与持久化层完全解耦。
- 系统需提供标准化的日志输出格式，便于通过 ELK 等工具进行故障定位。
